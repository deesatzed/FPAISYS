# S-SESE local contract v1 (design)

Status: proposed; no implementation or security validation is implied. All records carry `schema_version: 1`. JSON serialization for hashed records must be canonical and specified by implementation before data is written.

## Identity and events

A candidate ID is the full SHA-256 digest of its exact runtime artifact bytes, with the runtime and ABI version recorded separately. Store bytes immutably; recompute the digest before execution. An event has an integer nanosecond timestamp, entity ID, finite metric value, and flags. The host owns the window and passes an immutable snapshot; candidate results have a decision code, finite score, and reason code. Reject malformed inputs and outputs.

Telemetry stores duration in integer microseconds and timestamps in UTC with explicit units. Shadow results are observations and never determine champion output. Errors, timeouts, resource exhaustion, and missing results are explicit statuses rather than success.

## Replay and promotion

A replay pack has a version, immutable content digest, and at least one case. Each case has an ID, input state and event, expected verdict, and exact comparison rules. A replay run identifies candidate and pack digests, execution environment, per-case actual/expected results or errors, start time, and overall status. Malformed or empty packs and missing, stale, failed, or interrupted evidence fail closed.

New local synthetic event replays also append a versioned timing event in the same transaction as the replay. It links the replay event hash and records each executed case's ID, wall-clock start and finish in Unix nanoseconds, and elapsed monotonic nanoseconds. After an execution error, remaining cases are recorded as skipped with null timing; a verdict mismatch alone does not stop the run. Wall-clock values can move backwards; elapsed time includes worker supervision and is not a benchmark. Older replays without timing remain inspectable with unknown case timings, and v1 timing records retain their original behavior. These measurements are host assertions protected only by the retained ledger chain and checkpoint.

Candidate state is `registered -> replay_passed -> shadow_evaluated -> approved -> champion`; rejection or failed evidence cannot advance it. Promotion is an atomic transaction that checks the current champion, evidence, and a specific human approval tied to the candidate and evidence. Record previous champion for explicit rollback; never infer approval from an outcome. Define evidence freshness and concurrency behavior before implementation.

For new typed-event fixture selections, the selected replay must pass. Bootstrap rechecks the selected replay, including on databases containing older failed selections. Failed runs and older selections remain inspectable; this rule does not retroactively alter their history.

## Governance and outcomes

A decision event includes domain, candidate and evidence identities, the three review columns, actor, explicit approve/reject action, timestamp, and synthetic-data provenance. Outcome events reference a decision, carry pending/validated/falsified status, source, actor, and time. Record updates as new events, not in-place revisions. Validate allowed transitions and preserve original evidence. The chain contains the prior hash and canonical event bytes; verification checks ordering, hashes and links. Without an independently retained trusted anchor, a rewritten or truncated chain can appear internally consistent. Hashes are not signatures.

## Storage and exports

SQLite is local, with foreign keys enabled on every connection, transactions around state changes, and a schema version recorded via `PRAGMA user_version`. Migrations must run transactionally, refuse unknown future versions, preserve data, and be tested from an existing database. WAL behavior and crash recovery require tests, not assumptions.

Exports include event and candidate IDs, outcome source and synthetic status. Pending or unsupported records are excluded. SFT requires a validated decision and complete input/output provenance; DPO additionally requires an explicitly recorded comparable preferred and rejected pair, never an invented pair; RLVR requires an observed validated or falsified outcome and explicit reward derivation. Export schemas and exact eligibility must be versioned and tested before use.

Schema v33 adds caller-asserted synthetic prompt/response traces and optional explicit preference pairs linked to typed-event reviews. These capture missing fields but do not prove that a model produced a response, that a pair is comparable, or that an outcome was independently observed. They are not eligible for SFT, DPO or RLVR training export merely because an operator marks an outcome `validated`. The current synthetic evidence exports remain `training_ready: false`; a separate conditional synthetic export is available under explicit operator assumptions.

The `sese-synthetic-training-eligibility-v1` audit reports these exclusions separately: SFT needs verified trace origin and a validated observed outcome; DPO additionally needs an explicit comparable pair; typed-event RLVR needs verified trace origin, an observed resolved outcome, and a recorded reward derivation. Pending outcomes fail all three. A falsified outcome cannot satisfy SFT or DPO's validated-outcome gate. All existing v33 traces remain ineligible because their origin and any resolution are caller asserted. This audit defines negative gates for the present schema, not a complete positive eligibility policy. The conditional export and remaining verification matrix are in [training-export-v1.md](training-export-v1.md).

Schema v34 permits a ledger-bound, pre-decision selection of a separate synthetic follow-up replay case. Its selected input must differ from every input in the domain's reviewed fixture, and the follow-up check requires the selection to precede the review. A newly selected follow-up replay must pass; promotion rechecks any existing selection and rejects a failed replay. Promotion also requires the selection to precede the approval used for that promotion. The selected fixture is executed and visible before review; it is not a blinded holdout or independent evidence of real-world outcomes. Its result does not resolve an outcome or establish training eligibility.

Schema v35 can retain a derived synthetic follow-up comparison as a ledger-bound receipt. Inspection recomputes the comparison against the selected case and observation; a receipt is not a validated or falsified real-world outcome and does not establish training eligibility.

Resolved typed-event outcome evidence exports include any linked synthetic follow-up receipts, recomputed in the export snapshot; pending reviews are excluded. The assertion and the synthetic comparison retain separate provenance. Follow-up check and receipt JSON use v2 schemas and `records_outcome: false`, which describes the operation and does not assert the current outcome status.

Schema v36 stores checked synthetic trace and outcome attestation payloads, signatures, signer IDs, authority-configuration digest and checkpoint in a ledger-linked receipt. Receipt insertion and its ledger event are atomic. Inspection verifies stored bindings but does not recheck signatures; rechecking requires the original digest-pinned authority set. The standalone Python verifier can independently check receipt and parent-ledger bindings, but does not verify signatures. Neither verifier establishes authority custody, independent observation or training eligibility.

Schema v37 adds the equivalent atomic ledger-linked receipt for a checked synthetic preference claim. It preserves the signed payload, reviewer ID, configuration digest and checkpoint; signature rechecking requires the original pinned configuration. Comparability and reviewer independence remain unverified, and the receipt does not establish DPO eligibility.

The synthetic evidence-package check joins one trace/outcome receipt and one preference receipt in a single verified snapshot. It requires the same trace and authority digest, a supplied checkpoint covering both receipts, and valid signatures for all three configured roles. The returned outcome remains caller asserted, and the check cannot establish trust custody, independence, comparability or training eligibility.

The corresponding `sese-synthetic-signed-evidence-v1` inspection export contains the recorded decision, trace, explicit pair, asserted outcome, candidate and fixture provenance, and the exact canonical signed payloads and signatures. It requires both checkpointed receipts and rechecks all signatures in the export snapshot. It is not an SFT, DPO or RLVR export and is always marked `training_ready: false`.

## Open typed-event state reconciliation

The `bld1.md` sketch keeps separate event-metric and champion-latency windows: its mean uses metric values, while p99 uses measured champion latency in microseconds. It also tracks total events and the last nonzero host error. The current experimental `EventHost` instead stores nonnegative event metrics as a synthetic latency window, uses the bounded window length as `count`, and accepts `last_error` from the caller. Its p99 uses nearest rank; the sketch uses a floor-based index. These are different semantics, not an implementation of the sketch's telemetry.

Before treating typed-event telemetry as the sketched contract, define and version the count, percentile and error policies; persist metrics and measured latencies separately; decide how failed execution contributes latency and error; and add migration and restart tests. Existing v25 stream receipts encode the experimental metric-as-latency assumption and must not be silently reinterpreted as execution durations. Replay fixtures and demo expectations must identify the applicable semantics. No latency or performance conclusion follows from the current synthetic values.

### Experimental measured-v2 policy

The separate `EventState` / `MeasuredEventHost` experiment records bounded metric samples and elapsed champion-attempt durations separately. `count` is the total committed observations; `mean` uses retained metrics in [-10^12, 10^12]; p99 uses the sketch's sorted floor(0.99*n) index clamped to n-1. Duration is elapsed parent-observed microseconds, including worker startup and failed attempts, not isolated guest time. A failed champion attempt sets host error 500; success preserves the most recent nonzero error. Shadow results do not update these state fields. The big-endian `SES2` state encoding is distinct from existing v25 metric-only stream bytes.

This experimental path supports separate durable measured streams and measured champion domains; it does not migrate older streams. Its observations carry `state_semantics: measured-v2`; replay packs bind their semantics, and reviews require a match. Measured reviews may promote a measured-domain champion when all other gates pass. A future durable/replay implementation must preserve this separation and may not reinterpret older streams.
