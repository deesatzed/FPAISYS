# Training export contract: synthetic v1

A conditional synthetic export is implemented for selected records under explicit operator-declared trust. The exporter checks signatures and a recomputed synthetic follow-up, but cannot independently establish custody, independence, model origin, comparability or real-world truth. The operator must assess those assumptions; these rows are not independently verified training data. No model execution or model improvement is implied.

## Common evidence gates

An export operates on one verified database snapshot and checks an independently retained checkpoint. Each row must identify the candidate digest, replay and fixture digest/version, review and decision, trace, outcome, source, and synthetic status. A missing link, pending outcome, malformed record, or failed verification excludes the row. A missing checkpoint or mismatch with the supplied trusted checkpoint fails the export; the hash chain cannot authenticate checkpoint custody. The exporter must not publish partial output on integrity failure.

Trace provenance must bind the exact prompt and response bytes to their source, acquisition method, time, and a locally configured source authority. The authority must attest the bytes; a model identity or API call must not be inferred from supplied text. Outcome evidence must identify a separately configured observer, the observation method, evidence reference, observation time and an attestation over the decision and result. A distinct key alone does not prove independence: the operator must establish and document the authority relationship. Signatures establish control of a key, not truth, consent, fixture quality or independence. Synthetic observations must be labeled synthetic and must never be represented as real-world outcomes.

The trust configuration and retained checkpoint must be provided independently of the writable evidence database. Reject unknown or revoked authorities, unverifiable signatures, missing provenance, and evidence predating the decision. Exact key custody, revocation, retention and source-adapter mechanisms remain implementation decisions; the conditional synthetic exporter cannot establish these broader gates.

## Experimental synthetic attestation encoding

The Rust library can encode synthetic trace and outcome claims for signature verification. An experimental check can match signed claims to existing checkpointed records and retain them in a ledger-linked receipt; it does not establish trusted authorities. Each payload starts with the ASCII string `sese-synthetic-trace-attestation-v1` or `sese-synthetic-outcome-attestation-v1`, followed by a zero byte. It then contains positive review and replay IDs as signed 64-bit big-endian integers, followed by candidate digest, fixture digest and review ledger hash as 64-byte lowercase ASCII hexadecimal strings.

Trace payloads append prompt, response, source and acquisition method in that order. Outcome payloads append one byte (`1` validated, `2` falsified), then source, observation method and evidence reference. Each text field is UTF-8 preceded by an unsigned 32-bit big-endian byte length; fields must be nonblank and at most 16,384 bytes. Both payload types end with a nonzero unsigned 64-bit big-endian Unix nanosecond timestamp. Their distinct prefixes identify them as synthetic; neither format can represent non-synthetic evidence.

The outer signature message starts with `sese-evidence-attestation-v1` and a zero byte, followed by the authority ID and role, each encoded as a 32-bit big-endian byte length and UTF-8 bytes, then the payload byte length as an unsigned 64-bit big-endian integer and the raw 32-byte SHA-256 payload digest. Roles are `trace-source`, `outcome-observer`, and `preference-reviewer`. Typed verification requires the matching role and a caller-provided non-revoked authority. The experimental link checks enforce timestamp ordering and match the supplied checkpoint and recorded fields, but cannot authenticate timestamps, checkpoint custody, authority configuration, observation evidence reference, comparability or independence.

The synthetic preference payload begins with `sese-synthetic-preference-attestation-v1` and a zero byte, followed by the common reference, a positive signed 64-bit big-endian trace ID and 64 lowercase hexadecimal bytes for the trace ledger hash. It then contains length-prefixed UTF-8 prompt, preferred response, rejected response, source and comparability basis, followed by a nonzero unsigned 64-bit big-endian review time. The pair must be nonblank and distinct. The link check compares the prompt and explicit pair to the stored trace, but the signed comparability basis is an assertion, not proof.

An experimental `sese-authority-set-v1` JSON format contains an `authorities` array of objects with `id`, `role`, lowercase hexadecimal 32-byte `public_key`, and Boolean `revoked`. The library accepts 1–128 unique IDs and keys, rejects weak keys, unknown fields and unsupported roles, and limits the input to 65,536 bytes. It checks the exact JSON bytes against a caller-supplied SHA-256 digest before parsing. Lookup excludes revoked entries. The link check can resolve named signers from such a set; it reports the matching digest but does not authenticate its custody. Changing whitespace changes the digest. This is an input format, not an authority-management service or proof of independent control.

An experimental `sese-synthetic-trust-policy-v1` JSON document records operator declarations, not verified facts. It contains `authority_config_sha256`, an optional Boolean `training_export_allowed`, and 1–128 `declarations`; each names `trace_source`, `outcome_observer`, `operator`, `observer_relationship_basis`, and optionally both `preference_reviewer` and `reviewer_relationship_basis` (or both null). IDs must resolve to non-revoked authorities in the supplied pinned configuration. Each source/observer pair is unique, explanatory fields are nonblank, and the exact policy bytes must match a separately supplied SHA-256 digest. The 65,536-byte bounded input rejects unknown fields. `event-evidence-policy-check` rechecks the three signed receipts and their covering checkpoint in one snapshot, then matches their signer IDs to a declaration. The check cannot authenticate the operator or policy custody, establish the claimed relationships or comparability, or establish eligibility. This inspection remains `training_ready: false`; the separate conditional exporter requires `training_export_allowed: true`, additional format-specific checks, and explicit operator acceptance. Missing or false flags deny export, so older policies must be deliberately updated and re-pinned to permit it. The flag is an operator assertion, not proof of independence or custody. Inspection-only Rust previews require a non-export policy and mark every preview ineligible.

`event-common-policy-check` checks a trace/outcome receipt and its source/observer declaration without requiring any preference pair. It performs signature, checkpoint and ledger checks in one snapshot. It is an inspection prerequisite for SFT and RLVR, not an eligibility decision; the signed observations and operator relationship remain assertions.

Separately, `event-followup-outcome-check` checks whether a caller-asserted outcome recorded after a preselected synthetic follow-up receipt agrees with its recomputed fixture comparison, using a checkpoint covering both events. Agreement is not evidence that the operator used the receipt, that the fixture is independently selected, or that a real-world outcome is true; this check does not establish training eligibility.

`event-signed-followup-check` binds the signed observer claim to a specific preselected receipt by requiring method `synthetic-followup-receipt-v1` and evidence reference `sese-followup:RECEIPT_ID:RECEIPT_LEDGER_HASH`. It verifies both claim signatures and recorded fields, recomputes the receipt, requires the signed observation time to be no earlier than receipt creation and no later than outcome recording, and requires the outcome to agree with the fixture result. It does not store the bundle, authenticate timestamps or checkpoint/authority custody, establish observer or fixture independence, or prove a real-world outcome. The result remains ineligible for training.

`event-signed-followup-record` runs the same check and writes the existing attestation receipt and ledger event atomically. `event-signed-followup-recheck` requires the original bundle and a checkpoint covering that attestation receipt; it compares the bundle to retained payloads and signatures and recomputes the follow-up check in one snapshot. The receipt format is shared with generic attestations, so its existence alone does not attest that a follow-up check was performed. These operations do not establish training eligibility.

`event-retained-followup-check` can instead reconstruct the trace and outcome from the retained canonical bytes, reject noncanonical encodings and recheck signatures, record links and the follow-up with a caller-pinned authority set and covering checkpoint. It does not require the original bundle, but does not authenticate the authority or checkpoint custody or establish independence or training eligibility.

The inspection CLI accepts a `sese-synthetic-attestation-bundle-v1` JSON object with `schema`, integer `trace_id`, and `trace` and `outcome` objects. Each claim has `authority_id`, a 128-character lowercase hexadecimal `signature`, and an `evidence` object. Each evidence object contains `reference` with integer `review_id` and `replay_id` plus `candidate_sha256`, `fixture_sha256`, and `review_ledger_hash`. Trace evidence adds `prompt`, `response`, `source`, `method`, and integer `captured_unix_ns`; outcome evidence adds `outcome` (`validated` or `falsified`), `source`, `method`, `evidence_reference`, and integer `observed_unix_ns`. The bundle is limited to 131,072 bytes; unknown fields are rejected. The signature is over the canonical binary payload, not the JSON serialization. The tool does not generate signatures. The separate record command stores canonical payloads and signatures in a ledger-linked receipt, not the JSON bundle or authority set. Opening an older database can run the standard schema migrations.

The separate `sese-synthetic-preference-bundle-v1` object contains `schema` and `claim`, where the claim has `authority_id`, lowercase hexadecimal `signature` and `evidence`. Its evidence includes the same `reference` plus `trace_id`, `trace_ledger_hash`, `prompt`, `preferred`, `rejected`, `source`, `comparability_basis`, and `reviewed_unix_ns`. It uses the same input size and unknown-field rules. A separate record command stores the checked canonical payload and signature in a ledger-linked v37 receipt; rechecking requires the original pinned authority configuration. This does not verify comparability or establish DPO eligibility.

## Format-specific gates

| Format | Positive eligibility | Exclusions and label |
| --- | --- | --- |
| SFT | Common gates, an observed validated outcome, and a source-attested prompt/response. Export the exact response as the target. | Pending or falsified outcomes, unavailable trace origin, or inferred targets are excluded. |
| DPO | SFT gates plus an explicit preferred and rejected response for the same source-attested prompt and a separate preference attestation explaining comparability and choice. | Missing, identical, unrelated or inferred pairs are excluded. Do not construct a rejected response from a decision label. |
| RLVR | Common gates, a validated or falsified observed outcome, and a recorded versioned reward rule applied to that outcome. Preserve the rule and evidence reference with the scalar. | Pending, unobserved, untraceable or unmapped outcomes are excluded. A synthetic fixture comparison is a fixture result, not a real-world outcome. |

SFT and DPO require validated outcomes; RLVR can retain falsified outcomes. A proposed initial rule is `validated=+1`, `falsified=-1`, with no formatting bonus. Its provenance and version travel with each conditional row; the scalar does not establish real-world utility. The conditional schemas and single-record exclusion report are described below.

The experimental external `sese-synthetic-reward-rule-v1` JSON format specifies `version: outcome-sign-v1`, integer `validated: 1`, integer `falsified: -1`, and nonblank `actor` and `source`. It is limited to 65,536 bytes, rejects unknown fields and unsupported versions or mappings, and must match a separately supplied SHA-256 digest. `event-reward-preview` combines this rule with a checked synthetic trace/outcome receipt and emits the derived scalar alongside the rule version, digest, asserted provenance, and checkpoint. The input rule is not stored in the database; retain its exact bytes and pin independently. The preview is not a training row and does not establish custody or validate the asserted outcome.

## Required verification before enabling exports

For each format, test one positive synthetic record with controlled test authorities and an independently retained checkpoint, plus negative cases for pending and ineligible outcomes, changed prompt/response or evidence, altered candidate or fixture identity, missing and invalid signatures, unknown/revoked authorities, and a missing or changed checkpoint. Exercise restart and migration paths, transactional snapshots, and fail-closed output. DPO tests must reject fabricated or incomparable pairs; RLVR tests must verify both reward signs and reject unknown rule versions. Verify synthetic labels and complete provenance in every positive row.

These tests can prove only the implemented checks over synthetic data. Before non-synthetic use, separately establish authority governance, rights, privacy, source integrity and outcome validity; none follows from the test keys or hash chain. The conditional synthetic rows are eligible only under the operator's declared assumptions; they are not independently verified as training-ready.

## Conditional synthetic export

`event-training-export` emits one selected JSONL row on stdout and a structured inclusion or exclusion report on stderr. The CLI opens a current-schema v37 database read-only and does not run migrations; older databases require a separate migration. It verifies retained signed trace and outcome claims, their covering checkpoint, policy and a recomputed preselected synthetic follow-up in one snapshot. It rejects invalid or missing evidence without emitting a row. The trace ledger event must precede the outcome event, and its signed capture time must be no later than the signed observation time. This is an ordering check, not proof that the source timestamp is authentic. SFT and DPO require a validated result; DPO also requires a matching signed explicit preference and reviewer declaration. RLVR requires a separately pinned supported reward rule. Rows use `sese-synthetic-sft-v1`, `sese-synthetic-dpo-v1`, or `sese-synthetic-rlvr-v1`.

The literal `accept-synthetic-trust-v1` is a caller assertion, not identity authentication. The operator must separately assess and retain the authority configuration, policy, checkpoint and reward rule and their pins. Each row labels eligibility as conditional on operator-declared trust and explicitly marks custody, independence and real-world outcome as unverified; DPO also marks comparability unverified. The signed trace does not prove model origin. These fields must accompany any use of the row. The existing inspection and eligibility-audit commands retain their stricter `training_ready: false` results.

Controlled-key tests exercise all three formats and rejection cases. A controlled synthetic worker fault exercises a preselected passing follow-up that later mismatches, a signed falsified outcome, a -1 RLVR row, and SFT/DPO exclusion. The test changes a wrapper's behavior via a local marker without changing its digest; it is fault injection, not independent observation or worker attestation. The complete verification matrix above remains incomplete; test keys do not establish independent custody.

## Optional independent signature check

The Python ledger verifier accepts `--verify-event-signatures AUTHORITIES_JSON --authority-sha256 DIGEST` when the optional `cryptography` package is available. It checks Ed25519 signatures against a bounded, pinned authority configuration, requires the supplied checkpoint to cover all retained signature receipts, and fails if any receipt names a different configuration. It independently decodes each retained payload and compares references, fields and asserted timestamp ordering against stored records, including trace/outcome receipts without preference pairs. When combined with `--verify-event-followups`, the verifier also matches claims using `synthetic-followup-receipt-v1` to the recomputed local receipt and reports how many other outcome methods were not checked. It does not establish that a synthetic comparison is an independent or real-world observation. It reports the signature count and explicitly leaves strict weak-key validation unverified; PyCA verification has not been shown equivalent to Rust's strict verifier, so use the Rust check as well. Neither check establishes custody, independent control, timestamp authenticity, comparability or outcome truth.
